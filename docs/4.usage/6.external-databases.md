# External databases

A project can read a database it does not own, such as a client's MongoDB database. The provider module, `@antelopejs/mongodb`, reads and writes it in external mode, and a tables module declares the tables it maps. The database console lists each such database next to the project's own, and reads and edits its rows through the same pages.

## Connect a database

The console reaches an external database through two connections on its own module entry, both with the database's id: `@antelopejs/interface-database-catalog` describes it, and `@antelopejs/interface-database` reads and writes it. A database with only one of the two is not listed.

The first `@antelopejs/interface-database` entry pins the binding a plain import reaches, so it must name the project's own database. The entries after it are the named connections.

```ts fragment [antelope.config.ts]
"dms-database": {
  source: { type: "package", package: "@antelopejs/dms-database", version: ">=0.5.0 <1.0.0" },
  importOverrides: [
    { interface: "@antelopejs/interface-database", source: "mongodb" },
    { interface: "@antelopejs/interface-database", source: "mongodb-erp", id: "erp" },
    { interface: "@antelopejs/interface-database-catalog", source: "mongodb-erp", id: "erp" },
  ],
  config: {
    externalConnections: {
      erp: { access: "read" },
    },
  },
},
```

Here `mongodb` is the project's own database and `mongodb-erp` the provider of the external one. The connection id, `erp`, is the one the connect flow gives the database's other consumers. The tables the console reads are those the tables module declares on the same provider. The connection exists once the project restarts.

## Pick a database

The switcher at the top of the Database module's sidebar lists the project's database, then each external one with its engine and an **External** badge. Every page of the module shows the database picked there. The choice is kept per user.

| Feature | Own database | External database |
| --- | --- | --- |
| Overview, Schemas, Data browser | yes | yes |
| Rows: edit | yes | only when its access is `read-write` |
| Diagram, Query console, instances, a row's references | yes | no: the pages stay in the sidebar, locked |
| Migrations, schema edits, indexes | no | no |

## Large and slow databases

A customer's table can be large, and the console filters it in its own process, not in the database. On an external database:

- A search or a column filter reads at most the first 10,000 rows of the table, in the page's sort order. The grid lists the matches among them, and its footer counts those matches only. The API answers `capped: true` for such a page.
- The row count stops at 10,000: a larger table shows 10,000 rows in the footer, and its last pages end there.
- A page that takes more than 10 seconds answers `504` with "The external database did not answer in time: narrow the search or try again".
- The switcher waits at most 3 seconds for each database's catalog. A database that does not answer in time is still listed, without its engine, and its write access shows as not checked. The others answer as usual.
- A database that refuses, or does not answer, shows a generic message. Its driver's message, which can name the host, the port and the account, stays in the server log.

Only MongoDB external databases are tested. Other providers implement the same interfaces, but no test covers them.

## Allow changes

Each external database has one access, set in `config.externalConnections.<id>.access` on the dms-database entry:

- `"read"`, the default when the entry is absent: the console reads the database and refuses every edit with `403`.
- `"read-write"`: the console edits rows through the Data browser.

The project files are the only place the access is kept, so it is the same in every environment and versioned with the project.

In development, the bar at the top of the Data browser changes it, and the console writes it to `antelope.config.ts` through the DMS's configuration writer (`@antelopejs/interface-dms-builder`). Turning on **Read & write** asks for confirmation once: the database is the customer's live database, and the DMS cannot undo the changes made to it. Going back to **Read only** asks nothing. Outside development the bar shows the access and offers no toggle.

`"read-write"` needs an account that can write. The console reads what the connection's account may do from its catalog: the account can write when any relation the catalog lists grants it insert, update or delete. When it cannot, the toggle is locked with "This account can only read. Use an account with write access to allow changes." When the catalog does not answer, outside development for example, it is locked with "This account's write access could not be checked."

An edit names the database its page was opened on. When the user picked another database in another tab since, the edit is refused with `409` and the page asks to be reloaded.

## API

Every route answers the platform owner only. `<id>` is `own` for the project's own database, or a connection id.

| Route | Answers |
| --- | --- |
| `GET /api/database/connections` | `selected`, the database the user browses; `accessEditable`, whether the access may change here; and `connections`: for each database, `id`, `kind` (`own` or `external`), `label`, `engine`, `access`, `canWrite` (`true`, `false`, or `null` when the catalog does not answer), and the `unsupported` features |
| `PUT /api/database/connections/selected` | picks the database every page of the module reads, with `{ "connection": "<id>" }` |
| `PUT /api/database/connections/<id>/access` | writes the access with `{ "access": "read" }` or `{ "access": "read-write" }`. Development only, `403` elsewhere; `409` for `"read-write"` when `canWrite` is not `true`; `503` when no configuration writer is loaded |
| `GET /api/database/connections/<id>/relations` | the relations the catalog lists |
| `GET /api/database/connections/<id>/relations/<schema>.<name>` | one relation in full: columns, indexes, references |

The Data browser's routes (`/api/database/browse/*`) read the selected database. `PUT /api/database/browse/edit` also takes `connection=<id>`, the database the edit was made on, and answers `409` when it is no longer the selected one.

A relation `<schema>.<name>` of the catalog is table `<name>` of schema `<schema>`. An external database's tables have no instances, so a request on one names no `filter_instance`.
