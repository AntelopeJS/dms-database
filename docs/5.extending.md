# Extending

The module has no interface of its own to implement: it reads what the rest of the project already declares. This page explains what it picks up and how other modules use it.

## Supported extension boundary

Use registered database schemas, the Table watch trigger, configuration and deep links documented here. The runtime's root barrel also re-exports its page and route classes; those exports exist, but they do not define a separate extension SDK or a supported subclassing contract. Do not register those controllers again or depend on their implementation methods. Declare your own pages through `@antelopejs/interface-dms` and tables through the database interfaces instead.

## Your tables appear on their own

Every schema registered through `@antelopejs/interface-database-decorators` appears in the console, with its tables, columns, indexes and relations. There is nothing to add for the console:

```ts docs-check
import { BasicDataModel, Field, Index, RegisterSchema, RegisterTable, Table } from "@antelopejs/interface-database-decorators";

@RegisterTable("posts", "blog")
export class Post extends Table {
  @Field("string") declare _id: string;
  @Index() @Field("string") declare title: string;
  @Field("string") declare author: string;
}

export class PostModel extends BasicDataModel(Post, "posts") {}

export async function start(): Promise<void> {
  await RegisterSchema("blog");
}
```

Keep the table in `src/db/posts.table.ts`, import it from your module entry, and merge `RegisterSchema("blog")` into that entry's `start()` hook. `@Field` declares each column's storage type; `@Index` alone does not declare a field. Each instance of the schema (the default one, one per tenant, one per region) is listed in the instance pickers. Columns marked hashed, localized or encrypted carry a modifier badge.

::tip
Give a schema a readable badge with [`schemaLabels`](/docs/modules/database/configuration#schema-labels) rather than renaming it: schema IDs are part of the stored data.
::

## Automation nodes

When [`@antelopejs/dms-automation`](/docs/modules/automation/introduction) is loaded, the module registers two triggers, four actions and two data nodes. Without the automation module, the registration is a silent no-op.

The nodes that take a `connection` read `own`, the project's database, by default, or an external connection the project declares. An `instance` names an instance of the own database, such as a tenant id; empty is the default instance. An external database has no instances: a named instance or `allInstances` on one fails the step. An instance the schema does not list fails the step, or the activation of a trigger, so a typo does not read an empty table.

A step that fails says why in the run: an unknown connection, schema, table, column or instance, a refused filter, or an external database that did not answer within 10 seconds.

### Triggers

#### Table watch

**Table watch** (`database.table-watch`) fires a procedure on each insert, update or delete in a table, from the database change feed: in one instance, or in every instance through one feed.

| Config | Type | Required | Description |
| --- | --- | --- | --- |
| `schema` | `string` | yes | Registered schema ID, such as `shop`. |
| `table` | `string` | yes | Table name inside the schema. |
| `eventTypes` | `("insert" \| "update" \| "delete")[]` | no | Change types to fire on. Omit it for all three. |
| `instance` | `string` | no | The instance to watch. Empty for the default instance. |
| `allInstances` | `boolean` | no | Watch every instance through one feed. Refused together with an `instance`. |
| `includeAutomationWrites` | `boolean` | no | Also fire on the changes a procedure makes with **Run saved query**. Off by default. |

Each event passes this output to the procedure:

| Field | Type | Description |
| --- | --- | --- |
| `type` | `"insert" \| "update" \| "delete"` | The change. |
| `old` | `object \| null` | The row before the change: `null` on insert. See [Old and new rows](#old-and-new-rows). |
| `new` | `object \| null` | The row after the change: `null` on delete. |
| `schema`, `table` | `string` | Where the change happened. |
| `instance` | `string` | The instance of the changed row; empty for the default instance. |
| `at` | `string` (date-time) | When the module received it. |
| `originProcedureId`, `originRunId` | `string` | With `includeAutomationWrites` only: the procedure and the run whose write made the change. |

The rows leave out the store's instance tag. A run records them, so with `allInstances` every instance's rows reach the run history, as they reach the database console.

::warning
The trigger needs a database with a change feed. MongoDB only offers one on a replica set: on a standalone server, activation fails with "$changeStream is only supported on replica sets". A one-instance watch on MongoDB needs the collection to record change stream pre-images: activation fails with the command that turns them on when it does not. The trigger runs on one node of a cluster only, and reconnects once after a feed error. A change made while the feed is down, or while the cluster changes leader, is lost: the feed resumes from the time it reopens.
::

##### Changes a procedure makes

A change feed does not say who made a change. The module keeps, on each node, the writes **Run saved query** is running and has run in the last 10 seconds, with the table, the instance and the number of rows each changed. A change of that table and instance counts as the procedure's while its write runs, and after it for as many changes as the write reported. Table watch ignores those changes unless `includeAutomationWrites` is on, so a procedure does not answer its own writes.

With `includeAutomationWrites` on, a circuit breaker passes the changes of at most 5 writes of one procedure per watch within 60 seconds; the changes of later writes are dropped with a warning in the log. Every change of an admitted write passes, so one write of many rows is not cut short. It stops a procedure feeding itself, or two procedures answering each other.

The attribution has limits:

1. It sees the writes of the node that runs the watch. A run started by a trigger runs there, so a procedure fed by Table watch is always seen. A run started elsewhere, by **Run now**, a webhook or another node's trigger, writes unseen: its changes fire the watch like any other change.
2. A change a person or another module makes to the same table and instance while a procedure's write runs, or that reaches the feed before the write's own changes, can count as the procedure's: the watch then skips it unless `includeAutomationWrites` is on. One of the procedure's changes fires the watch in its place.
3. A write that does not report how many rows it changed, such as a write nested in another stage, counts every change of its table and instance for 10 seconds after it ends.
4. Writes other modules' procedures make, through their own actions, are not seen by this module.

#### Connection status

**Connection status** (`database.connection-status`) probes a connection on an interval and fires when it goes down or comes back up. The probe counts the rows of the first table of the connection with a 3 second deadline. The trigger runs on one node of a cluster only.

| Config | Type | Default | Description |
| --- | --- | --- | --- |
| `connection` | `string` | `own` | The connection to probe. |
| `intervalSeconds` | `integer` | `60` | Time between probes, kept between 30 and 3600. |
| `failuresBeforeDown` | `integer` | `2` | Failed probes in a row before the connection counts as down, 1 to 10. |
| `fireOn` | `("down" \| "up")[]` | both | The transitions to fire on. |

The first status the trigger sees is kept silently when the connection is up. When it is already down, the trigger fires `down` from `unknown`.

| Field | Type | Description |
| --- | --- | --- |
| `connection` | `string` | The connection id. |
| `status` | `"ok" \| "down"` | The new status. |
| `previousStatus` | `"ok" \| "down" \| "unknown"` | The status before. |
| `latencyMs` | `number \| null` | The probe's round trip; `null` when down. |
| `error` | `string \| null` | "The database did not answer in time" or "The database refused the probe: see the server log"; the raw error goes to the server log only. `null` when up. |
| `since` | `string` (date-time) | When the new status was first seen. |
| `checkedAt` | `string` (date-time) | When this probe ran. |
| `deliveryId` | `string` | `database.connection-status:<connection>:<status>:<since, to the minute>`. Two nodes that see the same transition during a leader change give the same id: dedupe on it. |

### Actions

Reads declare no side effects and run as they are in a test run.

| Id | Does | Inputs | Output |
| --- | --- | --- | --- |
| `database.get-row` | Reads one row by its primary key, straight from storage: DMS hooks and field modifiers are not applied. Hashed and encrypted fields are left out, both the field and its locked value under `_internal.data`. | `connection`, `schema`, `instance`, `table`, `id`. | `found`, `row` (JSON, dates as ISO strings, without the instance tag; `null` when not found), `primaryKey` (`null` when the table declares none). |
| `database.count-rows` | Counts the rows of a table, in one instance or every instance (own database only). | `connection`, `schema`, `instance`, `allInstances`, `table`, `filters` (up to 20 columns, all required: `is:<text>`, `contains:<text>`, or `<text>` for `is`, as the Data browser filters), `search` (case-insensitive text in any text, number or boolean column). A date column, a column the table neither declares nor shows in its first 10 rows, and an unknown mode are refused. | `count`. |
| `database.run-saved-query` | Runs a query saved in the query console, on the project's database. A query that inserts, updates, replaces or deletes runs only with `allowWrite`, checked on every run. A test run runs a read for real and measures a write without making it. Runs are not written to the console's history. | `queryId`, `allowWrite`, `maxRows` (1 to 1000, default 100). | `queryName`, `operation`, `mutation`, `simulated`, `rows` (what the query answers, as JSON), `rowCount` (rows read or changed; when simulated, the rows the write would touch, `null` when it cannot be measured), `truncated`, `durationMs`. |
| `database.health` | Probes a connection and counts its schemas, tables and rows. A connection that is down is an answer, not a failed step. Row counts are cached for 30 seconds, and a count that fails reads as 0. | `connection`, `includeStats` (default on), `largestTables` (0 to 50, default 10). | `connection`, `status`, `latencyMs`, `error`, `driver`, `checkedAt`, `schemaCount`, `tableCount`, `relationCount`, `indexCount`, `totalRows` (default instances; `null` without stats), `largestTables` (`{ schema, table, rows }`, largest first). |

Any saved query can be run by id: every console user is an owner and can already run it. Editing a saved query changes every procedure that runs it. `get-row` and `run-saved-query` put the rows they read in the run history; `run-saved-query` returns what the query selects, hashed and encrypted values included, as the console shows them.

### Data nodes

Both nodes compare the `old` and `new` rows a Table watch event carries, held in the run. They read nothing from the database: to read a row as it is now, use `database.get-row`.

| Id | Does | Inputs | Output |
| --- | --- | --- | --- |
| `database.row-diff` | Lists the top-level fields that differ. Objects compare whatever their key order, arrays in order. An insert lists every field of `new` as added, a delete every field of `old` as removed. | `old`, `new`, `ignore` (comma-separated fields, such as `updatedAt`). | `changed`, `fields`, `added`, `removed`, `before`, `after` (the values of `fields`, absent as `null`), `complete`. |
| `database.field-changed` | Tells whether one field differs. A dotted path reads a nested field. | `old`, `new`, `field`. | `changed`, `before`, `after`, `complete`. |

`complete` is false when both rows are missing, or when `old` holds only `_id` while `new` holds more: the rows cannot be compared, and nothing is reported as changed.

#### Old and new rows

| Store | `old` on update and delete | `new` on update |
| --- | --- | --- |
| MongoDB, one instance | The full row: the collection must record pre-images. | The row when the module read the change, which can include later writes, or `null` when the row was deleted since. |
| MongoDB, `allInstances` | The full row when the collection records a pre-image and still keeps it; otherwise only `{ _id }`, which gives `complete: false`. | As above. |
| PostgreSQL | The full row. | The row after the change. |
| MySQL, MariaDB | The full row. | The row after the change. |
| RethinkDB | The full row. | The row after the change. |

On MongoDB, an update whose row was deleted before the module read it arrives with `new: null`, like a delete: branch on the event's `type`.

## Roles and components

Each block of the module's pages carries `.meta({ name, icon, description })`, so the DMS role editor lists them and lets you hide one per role: the connection card, the schema cards, the largest tables, the recent queries, the table list, the inspector, the diagram, the data browser and the query console. The pages themselves stay reserved to the platform owner.

## Link to the console

The pages read their selection from the URL, so any page, notification or row action can deep-link into the console:

| Link | Opens |
| --- | --- |
| `/modules/database/schemas?record=<schema>::<table>` | The table inspector |
| `/modules/database/diagram?schema=<schema>&table=<table>` | The diagram, focused on a table |
| `/modules/database/data?schema=<schema>&table=<table>` | The table in the data browser |
| `/modules/database/query?schema=<schema>&table=<table>` | The query console on that table |

Add `instance=<name>` for a non-default instance, or `instance=all` for every instance.

## Frontend components

The module ships a Vue 3 frontend module registered under the `DmsDatabase` component prefix (`DmsDatabaseDataBrowser`, `DmsDatabaseQueryConsole`, `DmsDatabaseSchemaDiagram`, `DmsDatabaseTableInspector`, `DmsDatabaseConnectionStatus`). They are built for the module's own pages and backed by owner-only routes under `/api/database`: they are not a public API for other modules.

What decides a component's size is read with the page: the server renders it, and a client navigation waits for it (the Overview's connection probe and schema cards, the query console's schemas and library) instead of showing placeholders that the answer then resizes. A return to a page shows what was read before at once and reads it again behind it.
